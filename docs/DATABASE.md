# قاعدة بيانات CCE StableOS

## المرجع الأساسي وإعادة البناء

Supabase PostgreSQL هو مصدر البيانات. مخطط الجداول التشغيلية القديمة محفوظ في `supabase/baseline/legacy_core_schema.sql` لمشروع جديد فارغ فقط. جميع التغييرات اللاحقة مسجلة كملفات مرتبة في `supabase/migrations/`.

اختبار CI يبني قاعدة فارغة، يطبق ملف الأساس ثم جميع الترحيلات، ويختبر عقود الحجز والأمان وصحة الخيل. هذا لا يغني عن نسخة احتياطية وتجربة الترحيل على مشروع Supabase غير إنتاجي.

## العلاقات الجوهرية

| الجدول | الغرض | العلاقة الأساسية |
|---|---|---|
| `horses` | سجل الخيل والملخص التشغيلي | سجل واحد لكل خيل |
| `horse_health_profiles` | الحالة الصحية الحالية | واحد إلى واحد عبر `horse_id` |
| `horse_health_events` | التاريخ الصحي والمهام والتطعيمات | متعدد إلى واحد عبر `horse_id` |
| `profiles` | هوية العضو وبياناته | يرتبط بالمستخدم في Auth |
| `schedule` | جلسات الركوب والتدريب | ترتبط بالمدرب عبر `instructor_id` وبموعد الباقة عبر `booking_request_id + booking_slot_index` |
| `income` و`expenses` | الحركة المالية | يسجل `income` الإجمالي وحصة الإسطبل والمدرب دون تغيير رصيد العميل |
| `public_booking_services` | كتالوج الخدمة والسعر والسعة من الخادم | مفتاح ثابت `code` |
| `booking_requests` | دورة حياة طلب الحجز | يرتبط بالخدمة وبسجل دخل واحد |
| `booking_private_details` | هوية وسلامة الراكب المحمية | واحد إلى واحد عبر `booking_request_id` |
| `show_office_competitions` | السجل الرئيسي للبطولات | سجل واحد لكل بطولة |
| `show_office_classes` | برنامج فئات البطولة | متعدد إلى واحد عبر `competition_id` مع منع حذف البطولة التي تحتوي فئات |
| `show_office_riders` | سجل فرسان Show Office الدائم | مرجع UUID محمول واسم موحّد فريد |
| `show_office_horses` | سجل خيل المشاركات | مرجع UUID محمول وربط اختياري بـ`horses` عبر `core_horse_id` |
| `show_office_stables` | سجل الإسطبلات والأندية | مرجع UUID محمول واسم موحّد فريد |
| `show_office_entries` | مشاركات الفئة | فئة وفارس وخيل وإسطبل اختياري مع منع تكرار رقم البداية أو زوج الفارس/الخيل داخل الفئة |
| `show_office_class_judging` | دورة حياة تحكيم الفئة | سجل واحد لكل فئة بدأ تحكيمها |
| `show_office_entry_rounds` | النتيجة الرسمية لكل مرحلة | نتيجة واحدة لكل مشاركة و`first_round / jump_off` |
| `show_office_score_revisions` | سجل تصحيحات النتائج | سجل Append-only يحتفظ بما قبل وبعد كل تغيير |

## Show Office Sprint 1

يخزن `show_office_competitions` اسم البطولة وتاريخها ومكانها والمنظم والحكم الرئيسي ومصمم المسار والحالة والملاحظات. الحالات المسموحة فقط هي `Draft / Open / Running / Finished`، ويمنع الفهرس الفريد تكرار الاسم نفسه في التاريخ نفسه بعد إزالة المسافات الطرفية وتوحيد حالة الأحرف.

يسجل الجدول `created_by / updated_by` من `auth.uid()` و`created_at / updated_at` تلقائيًا. القراءة والإنشاء والتعديل والحذف محمية بصلاحيات `show_office.*` مستقلة.

## Show Office Sprint 2

يخزن `show_office_classes` الفئات التابعة لكل بطولة. `class_number` نصي لقبول أرقام تشغيلية مثل `1A`، و`sort_order` رقم صحيح موجب يحكم ترتيب العرض. تشمل الحقول الاسم، الارتفاع بالسنتيمتر، نوع المسابقة النصي، الوقت المسموح والحد الزمني بالثواني، Jump-Off، رسم الاشتراك بثلاث منازل عشرية، والملاحظات.

يمنع الفهرس الفريد تكرار رقم الفئة داخل البطولة بعد إزالة المسافات الطرفية وتوحيد حالة الأحرف. علاقة `competition_id` تستخدم `ON DELETE RESTRICT`، لذلك لا يمكن حذف بطولة قبل حذف فئاتها. الحذف فعلي وليس Soft Delete، ويضيف Sprint 3 علاقة `RESTRICT` من Entries إلى الفئة لمنع حذف فئة تحتوي مشاركات.

تستخدم الفئات صلاحيات `show_office.classes.view/create/update/delete` المنفصلة. يحصل Manager وSuper Admin عليها افتراضيًا. سياسات RLS مستقلة لكل عملية، ولا تمنح صلاحية عرض الفئات قراءة مباشرة لجدول المسابقات. توفر RPC المحدودة `cce_show_office_class_competitions()` فقط `id / competition_name / competition_date` اللازمة لاختيار البطولة الأب؛ تبقى بقية أعمدة المسابقة خلف `show_office.view` أو `show_office.competitions.view`.

### استعادة نسخ Show Office

يستخدم v4.12.0 الدالة `cce_restore_show_office_module(jsonb)` لاستقبال كائن يحتوي `competitions / classes / riders / horses / stables / entries / judging / scores`. النسخ القديمة التي لا تحمل كيانات Sprint 2 أو 3 أو 4 تعامل الحقول المفقودة كمصفوفات فارغة. تتحقق الواجهة وقاعدة البيانات من كامل الدفعة ومن جميع المراجع قبل الإكمال. أي صف غير صالح يلغي دفعة Show Office كاملة؛ استعادة الوحدة ذرية. الاستعادة العامة للجداول القديمة المتعددة تبقى Best-effort وقد تكتمل جزئيًا.

تفرض PostgreSQL الحدود نفسها التي تفرضها الواجهة: 180 حرفًا لكل من الاسم والمكان والمنظم والحكم الرئيسي ومصمم المسار، و4,000 حرف للملاحظات. لذلك لا يمكن لطلب مصادق مباشر تجاوز تحقق التطبيق.

الإدخال لا يمرر `id` أو `competition_id` المحمول أو `created_by / updated_by` أو الطوابع الزمنية. لذلك تختم Triggers السجلات الجديدة بالمستخدم الذي نفذ الاستعادة. تستخدم RPC `ON CONFLICT DO NOTHING` مع الفهارس الفريدة؛ السجلات الموجودة لا تُعدل وتحتفظ بهوية التدقيق الأصلية، ويعاد عدد مكررات المسابقات والفئات منفصلًا داخل `entities`.

## Show Office Sprint 3

لا يستخدم Sprint 3 نموذج Guest Rider. يحفظ الفارس والخيل والإسطبل/النادي كسجلات دائمة داخل Show Office، ويعيد استخدام الاسم بعد إزالة المسافات وتوحيد حالة الأحرف. يمكن ربط خيل موجود في سجل الإسطبل بواسطة `core_horse_id` دون فرض مالك أو بيانات تشغيلية على خيل المنافسات الخارجية.

`show_office_entries` يرتبط بـ`show_office_classes` و`show_office_riders` و`show_office_horses` و`show_office_stables` باستخدام `ON DELETE RESTRICT`. الحذف فعلي وليس Soft Delete؛ لا يمكن حذف فئة أو سجل مرجعي قبل حذف المشاركات التابعة. يحفظ `start_number` عددًا صحيحًا موجبًا، ويمنع فهرسان فريدان تكرار رقم البداية أو زوج الفارس/الخيل داخل الفئة.

واجهة Entries لا تكتب سجلات الدليل مباشرة. تستدعي `cce_save_show_office_entry` التي تتحقق من صلاحية العملية، تعيد استخدام الدليل أو تنشئه، ثم تحفظ المشاركة ذريًا. القراءة الكبيرة تستخدم `cce_show_office_entries_page` مع بحث وPaging خادمي. النسخة الاحتياطية تقرأ جميع الجداول بتصفح Keyset وتزيل IDs المحلية؛ عند الاستعادة تستخدم UUIDs المحمولة، وتستطيع مطابقة سجل موجود بالاسم الموحّد إذا اختلف UUID بين البيئتين.

## Show Office Sprint 4

يحفظ `show_office_entry_rounds` الوقت بوحدة millisecond في `time_ms`، والأخطاء الرسمية في `faults numeric(8,2)`، والرفض في `refusals`. الحالات `eliminated / retired / did_not_start` متنافية؛ DNS لا يحمل وقتًا أو أخطاء أو رفضًا. النتيجة المكتملة العادية تتطلب وقتًا وأخطاء. يمنع الفهرس الفريد أكثر من نتيجة للمشاركة والمرحلة.

الترتيب المؤقت يضع النتائج الصالحة حسب الأخطاء الرسمية المدخلة ثم الوقت، ويستخدم نتيجة Jump-Off عند وجودها في فئة تسمح بها. لا يحسب Sprint 4 عقوبات من Refusals أو Allowed Time، ولا يدعم Table C أو Optimum Time أو Two Phase. هذه قواعد مستقبلية ولا يجوز استنتاجها ضمنيًا.

`show_office_class_judging.status` هو `Not Started / Running / Finalized`. لا تقبل RPC الحفظ إلا عندما تكون البطولة `Running`. Finalize يتطلب نتيجة First Round لكل مشاركة ويقفل كل تغيير، وReopen يعيد الفئة إلى Running. `row_version` يزداد عند كل تصحيح ويجعل الحفظ أو المسح القديم يفشل بدل الكتابة فوق تحديث جهاز آخر.

لا تمنح الجداول الثلاثة أي كتابة مباشرة للمتصفح. القراءة محمية بـRLS، والكتابة تمر عبر RPCs ذات `search_path` ثابت وتحقق صلاحيات:

- `show_office.judging.view`: قراءة اللوحة والترتيب.
- `show_office.judging.score`: إنشاء وتصحيح ومسح النتائج.
- `show_office.judging.finalize`: اعتماد وقفل الفئة.
- `show_office.judging.reopen`: إعادة فتح فئة معتمدة.

يحصل Manager وSuper Admin على الأربع افتراضيًا. دور Judge يحصل على العرض والتسجيل فقط. يسجل Trigger كل Create/Update/Reset في `show_office_score_revisions`؛ حذف النتيجة لا يحذف تاريخها. علاقات `RESTRICT` تمنع حذف مشاركة لها نتيجة أو فئة لها سجل تحكيم قبل معالجة البيانات التابعة صراحةً.

نسخة Sprint 4 تصدر `judging / scores` من Supabase مباشرة بتصفح Keyset. لا تصدر سجل المراجعات بوصفه سجلًا أمنيًا محليًا للبيئة؛ إنشاء النتيجة المستعادة يولد Revision جديدًا باسم منفذ الاستعادة. تمنع الاستعادة مكررات UUID ومكررات Entry/Phase، وتتحقق من First Round قبل Jump-Off ومن اكتمال الفئة المعتمدة.

## قاعدة الحالة

لا يجوز استخدام `horses.status` لتخزين الحالة الصحية. الحالة التشغيلية والحالة الصحية مستقلتان:

- التشغيلية: `horses.status`.
- الصحية الحالية: `horse_health_profiles.health_status`.
- التاريخ والمهام: `horse_health_events`.

## الأحداث الصحية والملخصات القديمة

`horse_health_events` هو المصدر الأساسي. الحقول التالية في `horses` مدعومة مؤقتًا للتوافق:

| نوع الحدث المكتمل | حقول الملخص |
|---|---|
| Farrier | `farrier_date`, `farrier_name` |
| Dental | `teeth_date` |
| Deworming | `deworm_date` |
| Vaccination | `vaccine_date`, `vaccine_dr` |
| Medication | `med_date`, `medicant` |

ترحيل `20260719_security_database_foundation_v470.sql` يحفظ الملخصات القديمة أولًا كأحداث تاريخية، ثم يعيد احتساب هذه الحقول بعد `INSERT / UPDATE / DELETE`. مهام العناية تستخدم تاريخ الإكمال الفعلي في توقيت البحرين، أما السجلات التاريخية فتحتفظ بـ`event_date` المدخل.

## الحجوزات والمالية

- السعر، مدة الخدمة، عدد الحصص ووحدات السعة تأتي من `public_booking_services` ولا يقبلها الخادم من المتصفح.
- `cce_public_submit_booking` هو المسار الوحيد المسموح للزائر.
- الإدخال المباشر من `anon` إلى `income` ملغى.
- `income.booking_request_id` فريد ويربط السجل المالي بطلبه.
- حالة الحجز وحالة الدفع مستقلتان ولا يجوز استخدام `Paid` لتأكيد الموعد تلقائيًا.
- بيانات الهوية والصحة لا تُكتب في `income.notes`.
- ينشئ `cce_schedule_training_booking` سجلًا مستقلًا لكل عنصر في `booking_requests.session_slots`، ويسندها إلى المدرب المختار داخل معاملة واحدة.
- القيد الفريد على `schedule(booking_request_id, booking_slot_index)` يجعل العملية قابلة للتكرار دون مضاعفة الحصص.

## تقسيم إيراد التدريب

يحتفظ `income.amount_bd` بالقيمة الإجمالية المستحقة من العميل، ويحتفظ `income.paid_bd` بما دفعه فعليًا. لذلك يبقى المتبقي دائمًا `amount_bd - paid_bd`، وتبقى الإيصالات وكشوف العملاء على الإجمالي نفسه.

في `Lesson / Training` فقط، يضيف v4.8.0 القيم التالية:

| الحقل | القاعدة |
|---|---|
| `instructor_id` | المدرب المالي المستفيد من الدفعة |
| `training_split_enabled` | حد القطع: false للسجلات التاريخية، وtrue للتدريب الجديد |
| `stable_share_bd` | نصف `paid_bd` مقربًا إلى 3 منازل |
| `instructor_share_bd` | `paid_bd - stable_share_bd` |

في السجلات التاريخية وباقي الخدمات يكون `stable_share_bd = paid_bd` و`instructor_share_bd = 0`. لا يطلب النظام إسناد مدرب للسجل التاريخي. القيمتان مولّدتان من PostgreSQL ولا تكتبهما الواجهة، ويجب أن يساوي مجموعهما `paid_bd` دائمًا. لا يسمح النظام بدفعة تدريب جديدة مفعّل لها التقسيم دون مدرب نشط.

إسناد الحصة التشغيلية مستقل في `schedule.instructor_id` ويمكن تغييره إلى مدرب نشط آخر. يحتفظ `schedule.instructor` بنسخة اسم متوافقة تُحدّثها قاعدة البيانات تلقائيًا، لكن المعرّف هو المرجع الأساسي للبوابة والصلاحيات.

## الهوية والصلاحيات

- الحساب الجديد الناتج من Auth يحصل على Profile غير نشط وبدون دور.
- الإنشاء والتفعيل وتعيين الدور يتم من Edge Function الإدارية المحروسة.
- إيقاف التسجيل العام في إعدادات Supabase Auth مطلوب أيضًا؛ قاعدة البيانات تمثل خط الدفاع الثاني.
- سياسات `horse_health_events` تفحص `event_scope` وصلاحية Medical أو Vaccination أو Care المقابلة.
- قراءة بيانات سلامة الراكب تحتاج `bookings.sensitive.view` وتنتج سجل تدقيق.

## الطوابع الزمنية

أضاف v4.7.0 حقلي `created_at` و`updated_at` إلى `income` و`expenses` و`schedule` مع Backfill بتوقيت البحرين. يجب استخدامهما لترتيب آخر العمليات، بينما يبقى `date` هو التاريخ التجاري الذي أدخله المستخدم.

## تطبيق الترحيلات

1. أخذ نسخة احتياطية والتحقق من المشروع المستهدف.
2. تشغيل ملف Preflight الخاص بالإصدار وحفظ النتيجة.
3. تطبيق ملفات الترحيل بالترتيب على مشروع تجريبي.
4. تشغيل ملفات Verification واختبارات القبول لكل دور.
5. تطبيق الترحيل على الإنتاج في نافذة صيانة قصيرة، ثم نشر الواجهة المتوافقة مباشرة.
6. تسجيل النتيجة الفعلية في CHANGELOG.

تعليمات v4.7.0 موجودة في `docs/DEPLOYMENT_V470.md`، وتعليمات تقسيم التدريب في `docs/DEPLOYMENT_V480.md`، وتصحيح القطع التاريخي الإلزامي في `docs/DEPLOYMENT_V481.md`، وتعليمات إنشاء حصص الباقة في `docs/DEPLOYMENT_V482.md`، وتعليمات Show Office في `docs/DEPLOYMENT_V490.md` و`docs/DEPLOYMENT_V491.md` و`docs/DEPLOYMENT_V4100.md` و`docs/DEPLOYMENT_V4110.md` و`docs/DEPLOYMENT_V4120.md`. ملفات Rollback التوافقية لا تحذف بيانات وتستخدم للطوارئ فقط.

## ضوابط الأمان

- لا توضع Service Role Key أو كلمات المرور في المستودع أو الواجهة.
- تعتمد الكتابة الحساسة على RLS أو RPC محروس بالصلاحيات.
- وظائف `security definer` تستخدم `search_path` ثابتًا وأقل صلاحية ممكنة.
- لا يطبق ترحيل إنتاجي من جهاز غير موثوق أو دون خطة رجوع ونسخة احتياطية.
- لا تُعرض بيانات `booking_private_details` عبر استعلام مباشر في الواجهة.
- مدة الاحتفاظ الافتراضية للبيانات الحساسة 180 يومًا؛ أتمتة الإتلاف الدوري ما زالت بندًا تشغيليًا للمرحلة التالية.
