# قاعدة بيانات رشاد

## المرجع الأساسي

Supabase PostgreSQL مصدر البيانات الوحيد. مخطط الأساس يُحفظ في `supabase/baseline/`، والتغييرات اللاحقة كملفات مرتبة في `supabase/migrations/`، بنفس منهجية CCE: بناء قاعدة فارغة في CI، تطبيق الأساس ثم الترحيلات، واختبار العقود الحرجة (الصلاحيات، اعتماد دفعة الاستيراد، عزل بيانات الحالات).

## الجداول الجوهرية (تصميم أولي — يُفصَّل عند الترحيل الفعلي)

| الجدول | الغرض | العلاقة الأساسية |
|---|---|---|
| `profiles` | هوية المستخدم ودوره | يرتبط بمستخدم Auth؛ الدور: `counselor` / `student` / `super_admin` |
| `students` | سجل الطالب الأساسي | سجل واحد لكل طالب؛ `academic_id` فريد |
| `guardians` | بيانات ولي الأمر | متعدد إلى واحد عبر `student_id` (يُبنى لكن لا بوابة له في MVP) |
| `academic_terms` | الفصول/الأعوام الدراسية | مفتاح فريد (`year`, `term_label`) |
| `subjects` | كتالوج المواد | مفتاح ثابت `code` |
| `grade_import_batches` | سجل كل عملية استيراد | يحفظ نوع الملف، من نفّذ الاستيراد، الحالة (`Reviewing` / `Committed` / `RolledBack`) |
| `grade_import_rows` | كل صف مُستخرج قبل الاعتماد | يرتبط بـ`grade_import_batches`؛ يحفظ حالة المطابقة (`Matched` / `Ambiguous` / `Unmatched`) |
| `grades` | الدرجة المعتمدة نهائيًا | `student_id` + `subject_id` + `term_id`؛ يحمل `source_batch_id` للتتبّع |
| `grade_corrections` | سجل أي تعديل يدوي على درجة معتمدة | Append-only، يحفظ القيمة قبل وبعد ومن نفّذ التعديل |
| `department_plans` | خطة القسم السنوية | سجل واحد لكل عام دراسي |
| `department_plan_goals` | أهداف فرعية للخطة | متعدد إلى واحد عبر `plan_id` |
| `agenda_items` | الأجندة التنفيذية | يرتبط اختياريًا بـ`goal_id` |
| `reminders` | تذكيرات المرشد | مرجع عام `entity_type` + `entity_id` (طالب/نشاط/حالة/خطة دعم) بدل أعمدة مفتاح خارجي متعددة |
| `guidance_cases` | الحالات الإرشادية | `student_id` + نوع الحالة + حالة مفتوحة/مغلقة + المرشد المسؤول |
| `guidance_case_sessions` | جلسات متابعة الحالة | متعدد إلى واحد عبر `case_id`؛ **جدول محمي بأعلى مستوى صلاحية** |
| `support_plans` | خطط الدعم الفردية | `student_id`؛ يرتبط اختياريًا بـ`case_id` |
| `support_plan_actions` | إجراءات خطة الدعم مع حالة الإنجاز | متعدد إلى واحد عبر `plan_id` |
| `career_sessions` | جلسات التوجيه المهني | `student_id`؛ مستقلة عن `guidance_cases` |
| `appointment_requests` | طلبات مواعيد الطالب مع المرشد | ينشئها الطالب عبر RPC، يعالجها المرشد |
| `audit_logs` | سجل تدقيق موحّد | يسجل كل قراءة لجلسات الحالات وكل اعتماد دفعة استيراد |

## تصنيف البيانات وحساسيتها

| المستوى | الجداول | من يصل إليها |
|---|---|---|
| عام تشغيلي | `students`, `academic_terms`, `subjects`, `department_plans`, `agenda_items` | كل مستخدم مصادَق حسب دوره |
| أكاديمي شبه حساس | `grades`, `grade_corrections` | المرشد لكل طلابه؛ الطالب لبياناته فقط |
| حساس درجة أولى | `guidance_cases`, `guidance_case_sessions`, `support_plans` | المرشد المسؤول عن الحالة فقط + صلاحية إدارية صريحة؛ **لا وصول للطالب** إلى تفاصيل الحالة، فقط لخطة الدعم المُوجَّهة له صراحة إن قرر المرشد إتاحتها |
| تدقيق | `audit_logs` | قراءة إدارية فقط، لا حذف |

القاعدة الصارمة: لا يُخزَّن أي نص من `guidance_case_sessions` أو ملاحظات حساسة أخرى داخل `reminders.note` أو أي حقل عام قابل للعرض في لوحات مشتركة.

## دورة حياة استيراد الدرجات

1. رفع الملف → `grade_import_batches` بحالة `Reviewing`، والصفوف الخام في `grade_import_rows`.
2. كل صف يحمل حالة مطابقة: `Matched` (تطابق `academic_id` بثقة كاملة)، `Ambiguous` (تشابه اسم دون تطابق رقم)، `Unmatched` (لا تطابق).
3. لا يمكن اعتماد الدفعة (`Commit`) وفيها صفوف `Ambiguous` لم تُحسم يدويًا؛ صفوف `Unmatched` تُستبعد صراحة من الاعتماد ولا تُحفظ كتخمين.
4. الاعتماد عبر RPC واحدة ذرية: تكتب كل صف `Matched`/المحسوم إلى `grades`، وتُحدّث حالة الدفعة إلى `Committed`. فشل أي تحقق يلغي الدفعة كاملة.
5. `RollBack` دفعة `Committed` يحذف الدرجات المرتبطة بها فقط (`source_batch_id`) عبر RPC محروسة، ولا يمس درجات من دفعات أخرى حتى لو كانت لنفس الطالب/المادة.

## الهوية والصلاحيات (تصميم أولي)

- حساب Auth جديد يحصل على `profile` غير نشط وبلا دور، تمامًا كما في CCE؛ التفعيل وتعيين الدور من إجراء إداري محروس فقط.
- أدوار الإصدار الأول: `counselor`, `student`, `super_admin`. الأدوار المؤجلة (`department_head`, `teacher`, `guardian`) تُضاف كقيم جديدة في نفس تعداد الدور لاحقًا دون تغيير هيكلي.
- كل سياسة RLS على `guidance_case_sessions` و`support_plans` تتحقق من أن المستخدم هو المرشد المسؤول عن الحالة أو يملك صلاحية إدارية صريحة، وتُسجَّل كل عملية قراءة في `audit_logs`.
- الطالب يقرأ فقط عبر Views/RPC مقيّدة بـ`auth.uid() = students.auth_user_id`، لا استعلام مباشر مفتوح على جداول `grades` أو `support_plans`.

## تطبيق الترحيلات

نفس منهجية CCE: نسخة احتياطية قبل أي ترحيل، تطبيق على مشروع تجريبي أولًا، اختبارات قبول لكل دور (مرشد/طالب) قبل الإنتاج، وتسجيل النتيجة في `CHANGELOG.md`. لا يُطبَّق أي ترحيل من جهاز غير موثوق أو دون خطة رجوع.
